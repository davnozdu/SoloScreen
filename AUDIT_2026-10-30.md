## Находки

### P1 · Один битый профиль стирает профили всех устройств

`Sources/SoloCore/DisplayProfile.swift:138-154`

`stored()` разбирает весь словарь `[String: [DisplayProfile]]` одним
`JSONDecoder` и при любой ошибке возвращает `[:]`. `write()` вызывает `stored()`
перед записью — то есть следующее сохранение пишет пустой словарь плюс одну
новую запись. Все профили всех устройств исчезают молча, без записи в лог.

Триггер не гипотетический: `DisplayProfile.init(from:)` терпит отсутствующие
поля, но `PreferredMode` разбирается строго (`DisplayMode.swift:58-65`), так что
одна испорченная строка режима — откат на старую версию, сторонний клиент,
обрезанная запись — валит весь словарь.

Проверено пробой на реальном коде SoloCore:

```
до порчи: A=2 B=1
после порчи (у B испорчен mode): A=0 B=0
после добавления профиля в A: A=1 B=0
ключей в хранилище после записи: ["0000106b-00000001-00000001"]
```

Исправление: разбирать по устройству (`JSONSerialization` → по ключу →
`JSONDecoder`), при ошибке одного устройства отбрасывать только его; `mode`
читать через `decodeIfPresent(String.self)` + `PreferredMode(encoded:)`,
негодную строку считать `nil`. Плюс тест «порча одного устройства не трогает
остальные».

### P2 · Выбор обычного разрешения молча включает удвоенную плотность

**Отклонено 2026-10-30, не дефект.** Удвоенная плотность выбирается сознательно:
на живой панели она даёт заметно более чёткую картинку, и переход на неё — то,
чего и хотели. Поведение оставлено как есть; ниже — как оно устроено, чтобы
следующий аудит не открывал это заново.

`Sources/SoloCore/DisplayMode.swift:83-91`, `143-149`;
`Sources/SoloScreen/SettingsModel.swift:222-226`

`ModeSelector.best` ищет совпадение только по ширине, высоте и частоте, а
плотность берёт «как просили, иначе первый попавшийся». Задуманная уступка —
«удвоенного нет, возьмём обычный того же размера» — работает и в обратную
сторону: обычного нет, возьмём удвоенный. Плюс список частот строится без
учёта плотности, поэтому `resolutionBinding` всегда берёт максимальную частоту
разрешения, даже если она есть только у удвоенного варианта.

Проверено на срезе режимов XREAL One Pro из `Tests/SoloCoreTests/DisplayModeTests.swift:5-14`:

```
пользователь выбрал 1920×1080 обычный; частоты [120, 90, 60], берётся 120 -> 1920×1080@120 обычный
пользователь выбрал 1280×720 обычный;  частоты [120, 60],     берётся 120 -> 1280×720@120 чётко
```

То есть на целевых очках выбор «1280 × 720» переключает на режим с кадровым
буфером 2560×1440, вчетверо дороже по видеопамяти — ровно то, от чего
предостерегает комментарий в `DisplayMode.swift:79-82`.

Исправление: запасной переход по плотности разрешить только при
`preferred.isHiDPI == true`; `refreshRates`/`resolutionBinding` фильтровать по
плотности. Существующий тест `обычныйНеПодменяется` этот случай не ловит —
он про частоту, которая есть в обеих плотностях.

### P2 · Ошибка регистрации горячей клавиши исчезает

`Sources/SoloScreen/HotKeyManager.swift:73-82`, `Sources/SoloScreen/SettingsModel.swift:288-303`,
`Sources/SoloScreen/AppDelegate.swift:32-33`

`register` возвращает `Bool`, но все вызовы его игнорируют. Если сочетание
занято другим приложением (или назначено на вторую команду самого SoloScreen —
второй `RegisterEventHotKey` с тем же кодом вернёт ошибку), в лог попадает
строка, а в интерфейсе остаётся «назначено». Пользователь узнаёт об этом
только тем, что клавиша не работает, — и после перезапуска тоже, потому что
неудачное сочетание уже сохранено в `UserDefaults`.

Исправление: `SettingsModel` должен получать результат регистрации и
показывать отказ (и не сохранять сочетание, если оно не зарегистрировалось);
перед сохранением сверять с другим сочетанием.

### P2 · Локальная сборка и тесты без Xcode больше не работают

`Sources/SoloScreen/SettingsView.swift:746` (и весь файл),
`Scripts/test.sh`, `README.md:205-210`, `docs/.../2026-09-07-soloscreen-design.md:95`

`swift build` и `Scripts/test.sh` падают на CLT-only машине: SwiftUI-макросы
(`@State`, `@FocusState`) живут в `SwiftUIMacros`, который ставится только с
полным Xcode. `test.sh` чинит лишь пути к `Testing.framework`, но не это.
Спецификация и README обещают сборку скриптом «без зависимости от Xcode» —
обещание перестало быть верным после перехода настроек на SwiftUI
(коммит 8b38092).

Практическое следствие для аудита: локально нельзя ни прогнать тесты, ни
проверить правку в UI, единственный исполнитель — GitHub Actions. Это надо
либо починить (вынести модели из SwiftUI-файла, оставив `@State` только там,
где без него не обойтись, — но макросы всё равно нужны), либо честно написать
в README «нужен Xcode 16+».

### P2 · Простой ≈ 1 % CPU: интерфейс перестраивается каждые 2 с

`Sources/SoloScreen/Coordinator.swift:84-92` (таймер), `:523-525` (`notify`);
`Sources/SoloScreen/MenuBarController.swift:184-216`, `:268-271`;
`Sources/SoloScreen/SettingsModel.swift:28-36`

Сторожевой таймер каждые 2 с вызывает `refresh()` → `notify()` → `onChange`,
а тот безусловно делает `menuBar.refresh()` и `settingsModel.reload()`, даже
когда состояние не изменилось. В `refresh()`:

- `NSImage(systemSymbolName:)` создаётся заново (`MenuBarController.swift:270`).
  По sample это самая дорогая часть: ~2.5 мс на вызов, потому что новая
  картинка каждый раз заново строит глиф в CoreUI, минуя кеш AppKit;
- заново собираются два подменю (`rebuildProfileSubmenu`, `rebuildTrustedSubmenu`);
- заново читается `UserDefaults` (`HotKeyManager.stored`, `storedProfile`);
- `SettingsModel.reload()` пишет в `@Published` и **дополнительно** вызывает
  `objectWillChange.send()` (`SettingsModel.swift:35`) — двойная публикация на
  каждое обновление, то есть лишний проход `body` у 760-строчного вида.

Измерено на установленной 0.10.3: 0.58 с CPU за 60 с простоя. За сутки это
~14 минут CPU и постоянные пробуждения раз в 2 с.

Исправление: сделать `State` сравнимым и вызывать `onChange` только при
изменении (экраны, builtinEnabled, override); держать две готовые `NSImage`
вместо создания на каждый вызов; пересобирать подменю только при изменении их
содержимого; не трогать `settingsModel`, пока окно не открыто. Опрос экранов
оставить как есть — 81 µs раз в 2 с ничего не стоит, а вот хвост за ним стоит.

### P2 · Аварийный путь идёт в обход главного потока

`Sources/SoloScreen/Coordinator.swift:120-133`, `Sources/SoloScreen/AppDelegate.swift:139-144`,
`Sources/SoloScreen/BrightnessService.swift:36-42`

`restoreBeforeExit()` вызывается из очереди сигналов (`DispatchSource`), при
этом трогает `BrightnessService` (мутирует `appliedTo`, `level`, …) и
`DisplayKit`. Всё остальное состояние живёт на главном потоке, и `apply()`
может в этот момент как раз выполнять `CGSetDisplayTransferByTable`. Пакет
собирается в режиме Swift 5, поэтому компилятор об этом молчит.

Практический риск невелик (сценарий — только выход из приложения), но это
единственное место, где гонка реальна: либо сериализовать доступ через
`DispatchQueue.main.sync` с таймаутом, либо не хранить состояние в
`BrightnessService`, а восстанавливать гамму безусловно.

### P2 · Релиз собирается с неподписанным appcast

`Scripts/make-appcast.sh:19-27`

Если секрет `SPARKLE_PRIVATE_KEY` не задан, скрипт печатает предупреждение и
публикует `appcast.xml` с пустым `sparkle:edSignature`. При заполненном
`SUPublicEDKey` Sparkle такой файл отвергнет — обновление не придёт никому,
а релиз будет выглядеть успешным. Нужно падать (`exit 1`) и проверять, что
подпись сходится с публичным ключом из `Scripts/sparkle-public-key.txt`.

### P3 · Мелкие недочёты

1. `Coordinator.swift:200-202` — `defaults.set(...)` последнего ID встроенного
   экрана на **каждом** опросе, то есть запись в `UserDefaults` раз в 2 с без
   изменения значения.
2. `Coordinator.swift:394-399` — если режим из профиля стал недоступен,
   он остаётся в профиле, ошибка уходит только в лог, и при каждом запуске
   повторяется та же попытка. Пользователю стоит показывать «режим недоступен,
   выберите заново».
3. `DisplayKit.swift:156-196` — приватный список пересчитывается целиком на
   каждое применение режима (`:224-225`), с новой аллокацией буфера на каждый
   из 132–423 режимов: 5.3 мс на встроенном экране, ~17 мс на очках (расчёт по
   40 µs/режим; на живых очках не мерилось). Один переиспользуемый буфер и
   один `withUnsafeBytes` на запись дадут кратное ускорение.
4. `MenuBarController.swift:273-327` — подменю пересобираются и при открытом
   меню (таймер работает в `.common`), что грозит сбросом подсветки и
   закрытием вложенного меню на ровном месте.
5. `SettingsModel.swift:166-173` — кеш режимов не сбрасывается при
   переподключении устройства.
6. `ModeConfirmation.swift:14-40` и `Coordinator.swift:407` — окно
   подтверждения показывается на главном экране; если встроенный уже погашен,
   а выбранный режим сделал очки чёрными, подтверждать нечего и негде — только
   ждать 15 с отката.
7. `Coordinator.swift:162-170` — `prepareForSleep` меняет `state.override`
   без `notify()`, меню показывает устаревшее состояние до следующего опроса.
8. `DisplayKit.swift:213-234` — после применения режима нет обратного чтения и
   записи в лог того, что реально встало; «-> true» означает лишь успех
   системного вызова.
9. Мёртвый код: `DisplayKit.isEnabled` (`:109-111`), `UpdaterService.automaticallyChecks`
   (`:26-28`), `Coordinator.pendingDisplays` пишется снаружи, а не внутри.
10. Нет тестов на: порчу хранилища профилей, запасной переход по плотности,
    отказ регистрации горячей клавиши, `refreshRates` с двумя плотностями.
    Именно поэтому CI зелёный.
11. Спецификация устарела: `docs/...design.md:61` обещает «яркость не
    запоминается между подключениями», сейчас она живёт в профиле
    (`DisplayProfile.swift:12,32`).
12. Незакоммиченных изменений нет; локальные теги не подтянуты
    (`git fetch --tags` покажет `v0.10.3`).

## Что исправлено 2026-10-30

Правки лежат в ветке `audit-fixes`, проверяются на GitHub Actions: локально
собрать приложение нельзя (см. P2 про Xcode), поэтому тесты и сборка — только CI.

- `DisplayProfiles`: хранилище разбирается по устройству и по профилю, негодная
  запись отбрасывается одна, прежний кусок сохраняется в `DisplayProfilesBackup`,
  `mode` читается терпимо. Добавлен тест на порчу одного устройства.
  Проверено пробой: испорченный режим → профиль остаётся без режима, остальные
  устройства целы; испорченная запись целиком → теряется только она.
- Горячая клавиша: `SettingsModel` получает результат `RegisterEventHotKey`,
  неудачное сочетание не сохраняется и показывается в интерфейсе; проверяется
  дубль между двумя командами.
- Простой: `Coordinator.State` стал сравнимым, `notify()` вызывается только при
  изменении состояния; иконка строки меню кешируется; меню не пересобирается,
  пока открыто; `SettingsModel.reload()` больше не публикует изменения дважды и
  пишет только изменившиеся поля; кеш режимов сбрасывается при переподключении.
- `BrightnessService` защищён замком: аварийное восстановление из очереди
  сигналов больше не пересекается с применением гаммы на главном потоке.
- `make-appcast.sh` падает без приватного ключа и без публичного ключа,
  а не публикует неподписанный appcast.
- README и спецификация: сборка требует Xcode.
